# RetailPulse — Power BI Data Model

**Storage mode:** Import (not DirectQuery — see §5)
**Source:** the seven validated MySQL views, or the CSV extracts in `powerbi/data/`

---

## 1. Why the model is built on views, not base tables

This is the single most important decision in the model.

The raw tables sit at **four different grains**:

| Table | Rows | One row = |
|---|---|---|
| `orders` | 99,441 | one order |
| `order_items` | 112,650 | one product line |
| `order_payments` | 103,886 | one payment |
| `order_reviews` | 99,224 | one review |

Letting Power BI relate those directly would let a report author drag
`price` and a payment field onto one visual and silently inflate revenue.
**Measured on this data: joining items to payments inflates revenue by
+4.54%; an inner join to reviews moves it −0.47%.** Nothing errors; the total
is simply wrong.

`vw_order_summary` already collapses items, payments and reviews to **one row
per order**. Building on it makes that error structurally impossible rather
than relying on the author to remember.

## 3. Relationships

| From | To | Column | Cardinality | Cross-filter | Active |
|---|---|---|---|---|---|
| `dim_date` | `vw_order_summary` | `Date` → `order_date` | **1 : many** | Single | ✅ |
| `vw_order_summary` | `vw_review_summary` | `order_id` | **1 : many** | Single | ✅ |
| `vw_customer_summary` | `vw_order_summary` | `customer_unique_id` | **1 : many** | Single | ✅ |

**Deliberately NOT related:**

| Table | Why no relationship |
|---|---|
| `vw_category_performance` | Pre-aggregated to category × month. Relating it to the order fact would double-count. Page 3 is filtered by its own slicers |
| `vw_seller_performance` | Pre-aggregated per seller. Same reason |
| `vw_delivery_performance` | Pre-aggregated to state × month. Same reason |

> These three are **independent aggregate tables**, each powering one page.
> That is a deliberate choice: relating them would reintroduce exactly the
> fan-out the views were built to prevent. The cost is that Page 1 slicers do
> not cross-filter Pages 3–5; each page carries its own.

### Cardinality notes

- **`vw_order_summary` → `vw_review_summary` is 1 : many, not 1 : 1.** 547
  orders carry 2–3 reviews. Setting this to 1 : 1 would fail to refresh.
- **`vw_customer_summary` → `vw_order_summary` is 1 : many.** One person,
  up to 17 orders. Joining on `customer_unique_id`, **not** `customer_id`.
- All relationships are **single-direction**. Bi-directional filtering is
  avoided: it creates ambiguous paths and can produce wrong totals.

## 4. The date table

`dim_date` is generated by `scripts/export_powerbi_data.py`, covering
2016-09-04 → 2018-10-17 (774 contiguous days).

**It must be marked as the date table**: Modeling ▸ Mark as date table ▸
`Date`. Without this, `DATEADD`, `SAMEPERIODLASTYEAR` and `DATESINPERIOD`
silently return blank rather than erroring — a failure mode that is easy to
miss because nothing looks broken.

| Column | Purpose |
|---|---|
| `Date` | Relationship key, marked date column |
| `Year`, `Quarter`, `MonthNo`, `MonthName` | Hierarchy |
| `YearMonth` | `'YYYY-MM'`, matches `order_month` in the views |
| `YearMonthSort` | Sort-by column so `MonthName` orders chronologically, not alphabetically |
| `InStableWindow` | **Flags the 20 complete months (2017-01 → 2018-08)** |

`InStableWindow` matters: the dataset's edge months hold 4, 1, 16 and 4
orders, and **November 2016 is absent entirely**. Any unfiltered trend visual
shows a collapse that never happened, and will draw a straight line across
the missing month.

## 5. Import, not DirectQuery

| | Import | DirectQuery |
|---|---|---|
| Speed | Milliseconds (VertiPaq in memory) | 2–3s per visual against these views |
| Needs MySQL running | No | Yes, always |
| Full DAX available | Yes | Restricted |
| Data freshness | At refresh | Live |

The data is historical and static (ends October 2018) — there is no freshness
benefit to trade performance for. **Import mode, always.** Total model size is
roughly 48 MB uncompressed and compresses well in VertiPaq.

## 6. Column formatting to set in the model

Setting these once in the model means every visual inherits them.

| Column | Format |
|---|---|
| `order_revenue`, `order_freight`, `historical_value`, `revenue` | Currency, **R$**, 2 dp, thousands separator |
| `delivery_days`, `delay_days` | Decimal, 1 dp |
| `late_pct`, `on_time_pct` | Percentage, 1 dp |
| `review_score_avg`, `avg_review_score` | Decimal, 2 dp |
| `order_date` | Date, `dd mmm yyyy` |
| `customer_unique_id`, `order_id`, `seller_id` | Text — **never summarise** (set "Don't summarize") |

> Set "Don't summarize" on every ID column. Power BI defaults numeric-looking
> columns to Sum, which produces meaningless totals if one is dragged onto a
> visual by accident.
